# 当前项目 UI / 交互 / 前端结构优化分析

更新时间：2026-07-09

## 结论

当前项目已经具备可用的后台基础能力，但距离“可长期商用、可维护、可扩展”的后台体验还有明显差距。

最需要优化的不是单个页面颜色或按钮，而是以下四类基础问题：

1. 页面结构仍然过于集中，很多页面和业务逻辑堆在 `frontend/src/main.tsx`。
2. 通用 UI 组件太薄，页面状态、错误提示、确认弹窗、表格、详情抽屉没有统一标准。
3. CSS 已经变成补丁式累积，容易出现遮挡、不能滚动、窄屏错位、不同页面风格不一致。
4. 多商户、多国家、多数据量场景下，列表、筛选、统计、权限、状态反馈还没有形成稳定产品规范。

所以：还需要继续优化，而且建议按“基础组件和布局优先，高频页面其次，低频页面最后”的顺序做。

## 当前做得比较好的部分

- 已有基础色值变量和全局布局，说明项目已经开始向统一设计系统收敛。
- 会话页已经拆出部分模块，例如客服账号列表、客户列表、消息时间线、发送框等，方向是对的。
- 部分操作已经有 `AsyncButton`，能提供加载中、成功、失败反馈。
- 客户、会话、模型调用、总览等页面已经开始补时间筛选、分页、统计、导出能力。
- 后端已经有较多按商户隔离的数据接口，前端可以继续基于这些接口做更稳定的页面。

## 主要问题

### 1. 页面代码过度集中

现状：

- `frontend/src/main.tsx` 仍然包含大量页面、路由、配置、话本流程、会话等逻辑。
- `frontend/src/styles.css` 行数很大，多个页面样式混在一起。
- 某些页面已经模块化，但全局结构仍然不够清晰。

影响：

- 改一个页面容易影响另一个页面。
- 很难系统性检查“所有按钮是否有效”“所有页面是否可滚动”。
- 新增页面时容易继续复制旧写法，导致问题扩散。

建议：

- 把 `main.tsx` 拆成真正的页面入口：
  - `pages/DashboardPage`
  - `pages/ConversationsPage`
  - `pages/ScriptFlowsPage`
  - `pages/SettingsPage`
  - `pages/AiCallsPage`
- 每个页面只负责组合模块，不直接塞大量业务逻辑。
- 建立页面级目录：`page.tsx`、`hooks.ts`、`components.tsx`、`types.ts`。

### 2. 通用组件太浅

现状：

- `Table` 只负责简单渲染，没有统一的加载、失败、空状态、搜索无结果、分页、列密度控制。
- `Editor` 太通用，所有字段一口气铺开，复杂配置页会显得乱。
- 高风险操作大多还是 `window.confirm`，缺少统一影响说明。

影响：

- 每个页面自己处理状态，导致体验不一致。
- 用户点击按钮后是否保存成功、是否失败，经常不够明确。
- 删除、停用、启用、恢复版本这类操作风险提示不统一。

建议新增深模块：

- `PageShell`：统一页面标题、说明、右上角状态、时间切换。
- `DataTable`：统一加载、错误、空数据、分页、列省略、操作列。
- `FilterPanel`：统一时间筛选、商户、国家、客服账号、状态、搜索。
- `ConfirmDialog`：统一高风险二次确认。
- `DetailDrawer`：复杂信息统一放抽屉，不挤在表格里。
- `SettingsSection`：配置页分组、保存、检测、影响提示。
- `EmptyState` / `ErrorState` / `PermissionState`：所有页面统一状态。

### 3. 页面状态不完整

现状：

- 多处接口失败后直接吞掉错误，然后显示空列表。
- 空数据和接口失败在视觉上容易混在一起。
- 无权限状态没有统一组件。
- 局部刷新、保存失败、筛选无结果没有统一反馈。

影响：

- 用户不知道是“真的没数据”还是“接口失败了”。
- 你看到“按钮没反应”的根因，很多时候是失败被静默处理了。

建议：

- 所有列表请求必须返回四态：
  - 加载中
  - 成功有数据
  - 成功无数据
  - 失败
- 禁止页面级 `catch(() => [])`。
- 接口错误必须显示“发生了什么 + 下一步怎么做 + 重新加载”。

### 4. 表格和数据密度仍然偏拥挤

现状：

- 客户页、模型调用、话本流程、设置页都有字段过多的问题。
- 长文本、状态、内部字段容易撑开布局。
- 详情信息有时直接铺在页面中，导致右侧空白或下方延伸。

建议：

- 表格默认只保留 6-8 个关键字段。
- 次要信息放详情抽屉。
- 长文本统一省略，悬浮或点击查看全文。
- 操作按钮超过 2 个时收进“更多操作”。

### 5. 会话页还需要工程级稳定

现状：

- 会话页是当前最重要页面，也是复杂度最高页面。
- 已经有三栏结构，但仍然容易出现遮挡、滚动不一致、右侧辅助区占位过多。
- 客户列表、会话区、右侧助手区都有独立滚动需求。

建议：

- 会话页固定为三层布局：
  - 左侧客服账号，可收起。
  - 中间客户列表 + 对话框。
  - 右侧辅助抽屉，可完全收起。
- 每个区域独立滚动，禁止页面整体出现多个互相抢滚动条的区域。
- 右侧 AI 助手、客户资料、工单、历史记录用标签页或抽屉，不默认占满。
- 关键验证：
  - 1366×768 可用。
  - 1440×900 可用。
  - 1920×1080 不出现大面积空白。
  - 客户列表和聊天记录都能滚到底。

### 6. 设置页需要重新分组

现状：

- A2C、AI供应商、国家、客服账号、邀请码池、TG导师链接、自动回复、模拟训练、话本流程开关等都在设置页出现。
- 信息量太大，容易找不到入口。

建议：

- 设置页改成左侧配置分组：
  - 基础信息
  - 国家与语言
  - A2C 接入
  - AI 供应商
  - Telegram 通知
  - 邀请码池
  - 导师 TG 链接
  - 自动回复与模拟训练
  - 风险与接管规则
- 每个分组独立保存、独立检测、独立显示异常。

### 7. 话本流程需要从“能编辑”升级成“好编辑”

现状：

- 已经支持上传、内置 11 步、启用、删除、节点编辑。
- 但节点列表、节点详情、版本、启用状态放在一起时仍然显得重。
- 系统内置流程、副本流程、启用流程、兜底流程之间的差异需要在 UI 上解释清楚。

建议：

- 左侧流程版本列表，中间节点时间线，右侧节点编辑抽屉。
- 节点只显示中文业务名称，不显示内部英文标识。
- 节点编辑增加：
  - 客户说什么会进入此节点。
  - 当前节点要完成什么。
  - 是否发送注册链接。
  - 是否发送邀请码。
  - 是否发送注册教程图片。
  - 是否发送导师 TG 链接。
  - 满足什么条件进入下一步。
- 启用前做校验：
  - 是否有起始节点。
  - 是否存在断链。
  - 是否缺少必要链接/邀请码/TG链接配置。
  - 是否有节点会跳过确认 TG、下载 TG、发送 TG 链接。

### 8. 后台中文化还没有彻底完成

现状：

- 后台仍有 `Agent`、`AI`、`MiniMax`、`DeepSeek`、`Gemini`、`URL`、`CSV`、`JSONL` 等英文。
- 有些是品牌或技术名，可以保留；有些是系统字段或操作文案，应中文化。

建议：

- 建立“允许保留英文白名单”：
  - A2C
  - Telegram
  - WhatsApp
  - MiniMax
  - DeepSeek
  - CSV / Excel
- 其他后台操作文案必须中文化：
  - Loading → 加载中
  - Error → 加载失败
  - Delete → 删除
  - Save → 保存
  - Edit → 编辑
  - Agent 配置 → 接待专员配置 或 智能体配置

### 9. 性能和大数据列表仍需加强

现状：

- 部分页面仍有客户端分页、前端筛选、一次拉较多数据的风险。
- 客服账号、客户、会话、消息、模型调用这类数据量会越来越大。

建议：

- 所有大列表改为服务端分页。
- 搜索输入防抖。
- 复杂详情按需加载。
- 图片懒加载。
- 导出走后端任务或流式下载，避免前端卡死。

### 10. Playwright 验收还不够系统

现状：

- 有 Playwright 输出目录，但还没有形成“每个页面必须滚动、截图、点击关键按钮”的稳定验收门槛。

建议：

- 每次 UI 发布前跑：
  - 页面加载。
  - 截图。
  - 滚动到底。
  - 搜索筛选。
  - 打开详情。
  - 保存表单。
  - 删除二次确认。
  - 窄屏布局。
- 高频页面优先：
  - 会话
  - 客户
  - 设置
  - 话本流程
  - 总览
  - 模型调用

## 优先级建议

### 第一优先级：先解决反复出问题的基础设施

1. 重做 `DataTable`、`PageShell`、`FilterPanel`、`ConfirmDialog`、`EmptyState`、`ErrorState`。
2. 禁止静默吞接口错误。
3. 统一所有页面滚动容器。
4. 给高风险操作统一确认弹窗。
5. 为所有页面补 Playwright 滚动和点击测试。

### 第二优先级：高频页面体验

1. 会话页三栏布局稳定化。
2. 客户页增加更好筛选、详情抽屉、导出入口。
3. 设置页按配置分组重构。
4. 话本流程改成流程时间线 + 节点抽屉。
5. 总览和模型调用统计统一时间筛选体验。

### 第三优先级：长期可维护

1. 拆 `main.tsx`。
2. 拆 `styles.css`，按 layout/components/pages 分层。
3. 建立中文文案字典和允许英文白名单。
4. 建立版本记录和回滚入口。
5. 引入灰度 UI 开关，例如 `uiVersion=old/new`。

## 是否已经可以停止优化？

不建议停止。

目前系统业务能力已经很多，但 UI 和前端结构还在“功能堆叠阶段”。如果继续直接加功能，后面会越来越容易出现：

- 页面遮挡。
- 按钮点了无反馈。
- 状态没刷新。
- 数据多了卡顿。
- 表格横向撑开。
- 新页面风格不一致。
- 运营找不到入口。
- 问题排查困难。

更合理的做法是先做一轮“前端基础设施重整”，再继续追加业务功能。

## 建议下一步实施拆分

### 任务 1：UI 基础组件统一

产出：

- `PageShell`
- `DataTable`
- `FilterPanel`
- `ConfirmDialog`
- `EmptyState`
- `ErrorState`
- `PermissionState`
- `SettingsSection`

验收：

- 至少客户页、模型调用页、话本流程页迁移到新组件。
- 所有失败请求不再静默显示空数据。

### 任务 2：滚动和自适应验收

产出：

- Playwright 测试覆盖 6 个核心页面。
- 检查 1366×768、1440×900、1920×1080。

验收：

- 所有需要滚动的页面可滚到底。
- 会话页三栏不互相遮挡。
- 窄屏下不出现关键按钮不可见。

### 任务 3：设置页和话本流程重构

产出：

- 设置页分组。
- 话本流程时间线。
- 节点编辑抽屉。
- 启用前校验。

验收：

- 商户能清楚知道每项配置影响什么。
- 话本流程能看懂、能改、能启用、能回滚。

### 任务 4：中文化与状态规范

产出：

- 后台中文文案白名单。
- 状态标签统一映射。
- 空状态、错误状态、无权限状态统一。

验收：

- 后台不出现未翻译操作英文。
- 内部字段不直接暴露给运营。
